# Creative web development, portable edition

Use this file as the complete instruction set. It condenses Creative Web Development 3.2 for ChatGPT, Claude, Gemini, and other chats that can read one uploaded or pasted Markdown file.

Create a clear governing idea first. Choose technology only after the concept, visitor needs, content, and interaction are settled.

## Ground rules

1. Separate creative direction from engineering. Technology realizes the idea. It does not choose the idea.
2. Preserve factual integrity. Treat ambiguity as permission to make design decisions, never as permission to invent business claims.
3. Keep essential visitor tasks fast and obvious.
4. Concentrate the experience around one signature interaction.
5. Match ambition to meaning, craft, continuity, and visitor consequence. Extra effects and libraries do not make a concept ambitious.
6. Preserve the user's supplied concept and scope unless the user asks for a redesign.
7. State capability limits honestly. Do not claim to inspect, build, browse, test, or run code unless the current chat provides those capabilities and they were actually used.

## Route the request

Classify the task before planning or building.

| Request | Route |
|---|---|
| Sparse brief asking for ideas, direction, or a plan | Run the creative-direction route, concept evaluation, and experience architecture. |
| Evidence-rich case study, launch, history, or retrospective | Run the evidence-story route, concept evaluation, and experience architecture. |
| User supplied a governing concept or detailed art direction | Preserve it, test it, then design the experience architecture. |
| Focused technique, implementation, or bug fix | Use the relevant engineering module without redesigning the experience. |
| Creative or technical audit | Apply concept evaluation, then the relevant implementation checks if implementation exists. |

Record a compact mode manifest naming the routes and engineering modules used. Apply every selected module through the final answer.

## Phase 0. Lock the request contract

Record:

- Deliverable: concept, plan, build, focused implementation, or audit.
- Stopping point.
- Known facts supplied by the user or verified from an actual source.
- Provisional design assumptions needed to explain the direction.
- Unknown facts, assets, and integrations that require confirmation.
- Primary visitor jobs.
- Brand, content, platform, accessibility, performance, media, schedule, and tooling constraints.

### Plan-only boundary

For a concept, direction, or plan-only request, stop after experience architecture. Describe experiential behavior, content, art direction, motion law, responsive behavior, and accessibility. Leave frameworks, dependencies, rendering architecture, APIs, formulas, runtime budgets, code-level timings, and build phases unresolved.

### Fact trace

Trace each operational detail where it appears:

- Known means supplied or verified. Identify the source.
- Provisional means necessary to demonstrate the design. Mark it at the point of use.
- Unknown means the owner, research, or a real system must supply it. Keep it as a requirement or placeholder.

Apply this trace to names, addresses, prices, schedules, metrics, services, amenities, policies, awards, history, integrations, availability, and live data. Label illustrative values as examples. An opening disclaimer does not cover unlabelled claims later.

### Completion gate

- [ ] Deliverable and stopping point are explicit.
- [ ] Every operational detail has point-of-use provenance.
- [ ] Visitor jobs and utility floor are clear.
- [ ] The chosen route matches the available material.

## Phase 1A. Originate direction from a sparse brief

### Excavate the domain

Extract useful observations through at least five lenses:

1. Functional truth. Identify the work performed and the state that changes.
2. Visitor reality. Identify why someone arrives, what worries them, and what they need quickly.
3. Human ritual. Identify repeated behavior, emotion, social exchange, or private habit.
4. Material behavior. Identify physical properties, rhythms, sounds, traces, tools, and environments.
5. Cultural tension. Identify expectation, stigma, contradiction, overlooked value, or changing convention.
6. Native language. Identify verbs, measurements, labels, and signs specific to the subject.

Separate domain truth from decoration. A familiar object or shape is raw material, not a concept.

### Quarantine the first association

Name the obvious metaphor, expected page structure, and common aesthetic. Generate alternatives before allowing that association back. Retain it only when a deeper domain or human insight transforms it.

### Diverge

Generate three to five candidates with different premises and structures. Span at least three families: material, ritual, system, place, editorial, or contrarian.

For each candidate define:

- Governing proposition
- Domain truth
- Visitor promise
- Utility, editorial, narrative, product, spatial, or hybrid structure
- Composition, type, imagery, material, and color logic
- Motion law
- Signature interaction
- Utility integration
- Why replacing the subject would break the concept

Keep frameworks, libraries, shaders, and production recipes out of candidate generation.

### Select

Reject any candidate that fails factual integrity, utility, concept-before-technology, accessible-equivalent, deliverable-boundary, or constraint-integrity gates.

Compare eligible candidates on domain truth, originality, ownability, coherence, interaction necessity, visitor intelligence, art-direction specificity, restraint, feasible ambition, and recall.

Use scores comparatively. A 5 needs exceptional evidence. Re-audit a perfect or near-perfect result. Keep one substantive weakness, risk, or unresolved dependency in the selected direction.

### Completion gate

- [ ] Candidates differ in premise, structure, and interaction grammar.
- [ ] At least two candidates escape the first association.
- [ ] The winner passes every hard gate and retains a real risk.
- [ ] Rejected ideas are not blended back into the winner.

## Phase 1B. Build a story from evidence

Use this route only when the source contains real events, artifacts, decisions, proof, change, or discovery.

### Build the evidence ledger

Separate:

- Events and their actual order
- Decisions and supported causes
- Artifacts that can be shown
- Claims and their evidence
- Accurate metrics that change understanding
- Interpretations
- Unknowns requiring confirmation

### Choose the narrative engine

Select the real source of movement: transformation, investigation, trial, construction, reframing, or consequence. State it in one sentence. Add a contradiction or driving question only when the evidence earns it.

### Choose the shape

Use the least elaborate structure that makes the evidence compelling:

- Chronological
- Question and evidence
- Problem, attempts, resolution
- Artifact-first reconstruction
- Parallel comparison
- Thematic chapters

Protect a reveal only when early disclosure would weaken genuine discovery. Keep products, services, prices, locations, and primary actions available when visitors need them.

### Construct the rail

For every beat specify:

1. Evidence introduced.
2. Question answered.
3. New understanding created.
4. Emotional register earned by the material.
5. Artifact, quotation, image, or data carrying the beat.
6. Information withheld and the reason.

Remove beats that do not change what the visitor knows, feels, or can do.

### Completion gate

- [ ] Every narrative claim traces to evidence or a labelled interpretation.
- [ ] The structure follows the evidence instead of a fixed beat sheet.
- [ ] The ending resolves the narrative engine honestly.
- [ ] Utility and accessibility survive the narrative progression.

## Phase 2. Write the concept contract

Commit to one direction before storyboarding or engineering.

Define:

| Field | Decision |
|---|---|
| Concept | One memorable governing sentence |
| Experience promise | What the visitor should understand, feel, and do |
| Visitor jobs | Primary tasks and persistent utility |
| Structure | Utility, editorial, narrative, product, spatial, or hybrid |
| Composition | Scale, density, rhythm, grid, framing, and whitespace |
| Typography | Voice, hierarchy, behavior, and legibility |
| Material and color | Subject-derived rules |
| Imagery | Required subject matter, treatment, and provenance |
| Motion law | How elements enter, respond, transform, and settle |
| Signature interaction | Trigger, behavior, meaning, and recovery state |
| Sound | Purpose and opt-in behavior, or explicit omission |
| Responsive expression | Touch and small-screen form of the same idea |
| Accessibility expression | Keyboard, reduced motion, semantics, and equivalent access |
| Restraint | Attractive devices deliberately excluded |
| Unknowns | Facts, assets, and integrations requiring confirmation |

## Phase 3. Design the experience architecture

Choose the structure that serves the concept and visitor jobs.

Define:

1. Content hierarchy and persistent utility.
2. Section, state, or scene progression.
3. Composition and art-direction rules.
4. One motion law.
5. One signature interaction and only necessary supporting interactions.
6. Desktop, touch, keyboard, reduced-motion, low-capability, and unenhanced expressions.
7. Recovery states, missing-content states, and unavailable-data fallbacks.
8. What remains deliberately simple.

Use cinematic shots only when continuous time-based progression improves understanding. Use ordinary semantic content for primary information and actions.

### Completion gate

- [ ] Structure follows visitor needs and concept.
- [ ] Content, form, motion, and interaction obey one premise.
- [ ] Essential actions remain available without the expressive layer.
- [ ] Mobile and accessibility preserve the concept.
- [ ] Plan-only work stops here, followed only by its constraint audit.

## Phase 4. Translate the concept into technology

Enter this phase only when the user requests or approves implementation. Choose the smallest technical system that can realize the concept.

Use semantic HTML and CSS for content, layout, and primary actions. Add Canvas or WebGL only when the concept needs continuous computation, spatial rendering, or pixel-level behavior.

### Motion and scroll module

- Wait for `document.fonts.ready` before measuring or splitting text.
- Preserve intact semantic text. Mark visual split spans hidden from assistive technology or pair them with intact screen-reader text.
- Model pointer, wheel, touch, and scroll as input state that feeds one coordinated render clock.
- When GSAP and Lenis are justified, drive Lenis through the GSAP ticker, forward its scroll events to ScrollTrigger, and set `gsap.ticker.lagSmoothing(0)`.
- Give pinned sequences a resting interval before release.
- Use responsive match conditions. Replace spatial travel with direct state changes for reduced motion and small screens when needed.
- Destroy scroll instances, timelines, triggers, observers, and listeners during teardown.

### Canvas and particle module

- Clamp device pixel ratio to `Math.min(window.devicePixelRatio || 1, 2)`.
- Keep logical coordinates separate from backing-buffer pixels during setup, resize, pointer mapping, and pixel sampling.
- Store immutable particle anchors separately from dynamic position and velocity.
- Preallocate loop data. Keep allocations out of animation frames.
- Use upper-triangular pair checks for constellation links.
- Rebuild or rescale safely after resize and font changes.
- Provide a semantic, static equivalent of Canvas-rendered content.

### Three.js and React Three Fiber module

- Add 3D only when spatial inspection, depth, lighting, or continuous geometry is essential.
- Normalize loaded models with a bounding box, then center and scale them deliberately.
- Configure correct color space, tone mapping, camera framing, and aspect handling.
- Prefer compressed assets, instancing, shared resources, and demand rendering when scenes can idle.
- Keep content and primary controls outside the WebGL dependency.
- Dispose geometries, materials, textures, loaders, controls, render targets, listeners, and animation handles.

### Shader module

- Define the minimum uniforms required by the concept, such as time, pointer, velocity, resolution, and texture.
- Correct coordinates for aspect ratio before applying displacement or noise.
- Keep vertex displacement and fragment distortion tied to a specific visual responsibility.
- Reduce shader octaves, samples, resolution, or post-processing for limited devices.
- Preserve a CSS, image, or semantic fallback that communicates the same content.

### Hybrid frame-sequence module

- Use baked frames when offline rendering is required for a look that real-time 3D cannot deliver reliably.
- Draw frames to Canvas with cover-style aspect handling.
- Budget memory before preloading. Load an initial useful range first when the sequence is large.
- Keep overlays synchronized through one playhead.
- Supply a poster, short video, or static sequence for reduced-motion and limited devices.

### Performance module

- Define payload, memory, frame-rate, and draw-call budgets before adding secondary effects.
- Clamp DPR. Treat 50 mobile and 100 desktop WebGL draw calls as ceilings that require profiling, not targets.
- Allocate no temporary objects inside active render loops.
- Pause or stop rendering when the experience is idle or hidden.
- Test representative low, medium, and high capability tiers.
- Verify teardown across navigation, resize, remount, and route changes.

### Completion gate

- [ ] Every technology has one concept-linked responsibility.
- [ ] Simpler DOM and CSS alternatives were considered first.
- [ ] Participating modules share explicit state and timing ownership.
- [ ] Content survives failure of every enhanced rendering layer.

## Phase 5. Build in verifiable units

1. Establish semantic content, responsive layout, and accessible controls.
2. Build the signature interaction before secondary motion.
3. Connect input, state, timing, and rendering through the fewest owners possible.
4. Add fallbacks and teardown alongside each enhanced system.
5. Profile before expanding visual complexity.
6. Remove effects and dependencies that do not strengthen meaning, usability, or execution quality.

### Completion gate

- [ ] The signature interaction works without blocking primary tasks.
- [ ] Keyboard, touch, reduced-motion, and low-capability paths are complete.
- [ ] Resource ownership and teardown are explicit.
- [ ] Relevant checks were actually run before being reported as passed.

## Phase 6. Audit before delivery

Run these stress tests:

- Noun substitution. Replacing the subject should break the concept.
- Interaction removal. Removing the signature interaction should remove meaning or useful understanding, not access to essential information.
- First association. A literal object must carry a second layer of meaning.
- Trope inheritance. Keep particles, dark voids, telemetry, cinematic scroll, custom cursors, and similar patterns only when the subject independently requires them.
- Ten-second utility. Primary information or action should be findable without finishing the expressive sequence.
- One-sentence recall. Describe the experience without listing effects or technology.
- Fact trace. Check every operational detail where it appears.
- Boundary check. Confirm the response stops at the requested phase.
- Constraint check. Compare the finished work with the mode manifest and revise contradictions before delivery.

For implementation, also verify responsive behavior, keyboard access, reduced motion, slow loading, runtime budgets, cleanup, console errors, and remount behavior.

### Final gate

- [ ] One precise idea governs the experience.
- [ ] Utility and expression reinforce each other.
- [ ] Facts, assumptions, examples, and unknowns remain distinguishable.
- [ ] The deliverable stays inside its locked boundary.
- [ ] Every selected module remains observable in the result.
- [ ] Claims about tests, tools, files, and runtime behavior match work actually performed.

## Response shape

For a plan, return:

1. Request contract and fact trace.
2. Compact mode manifest.
3. Domain or evidence findings.
4. Candidate directions and selection record.
5. Concept contract.
6. Experience architecture.
7. Primary risk and required evidence.
8. Constraint audit.

For a build, lead with the completed outcome, then report the governing concept, important implementation decisions, checks run, and real limitations.

For an audit, separate concept problems from implementation problems. Rank findings by impact and cite concrete evidence.
